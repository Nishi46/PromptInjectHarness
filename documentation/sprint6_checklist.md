## Implementation decisions for this project's Sprint 6

**D1 — Composition is not "just pass a list to `DefenseStack`"; per-layer attribution needs new plumbing.** `DefenseStack` (`defenses/stack.py`) already accepts an ordered `list[Defense]` and already composes all four hooks correctly for *execution* (blocking, mutation-threading, `cost()` summing) — S1-02 genuinely built this. But nothing above it can see *inside* a composed stack today:

- Both adapters' recorder wrappers (`agentdojo_adapter.py`'s `_DefendedFunctionsRuntime`, `mcp_adapter.py`'s equivalent) call `defense_stack.on_pre_generate`/`on_pre_tool_call`/`on_tool_result` exactly **once per hook**, treating the whole stack as one atomic call, and log exactly one `_DefenseEventRecord` (hook/verdict/reason/timestamp — no defense identity at all) per call.
- `_write_episode_trace`/`_write_mcp_episode_trace` write every `defense_event.defense_name` and every `defense:<name>` `cost_record.model` from **one outer `defense_name: str` parameter** (today, always a single registered defense's own name) — never per stack member.
- `DefenseStack`'s own docstring already flags this exact gap: *"With more than one reason-setting member in the same stack (Sprint 6 composition), only the last one survives here."*

For a composed pair, this means today's trace DB cannot answer "which of the two defenses fired" or attribute cost to the right layer at all — exactly the two things S6-01 is named for ("cost attributed per layer") and S6-04 needs (naming the *shared failure mode*, which requires knowing which member did what).

**Decision:** extend `DefenseStack.__init__` to take `list[tuple[str, Defense]]` (name, instance pairs) instead of a bare `list[Defense]`, and have each hook method additionally record the *per-member* `HookResult`s it saw (e.g. a `self.last_member_results: list[tuple[str, HookResult]]` populated fresh on every hook call, read by the adapter immediately after). This is a smaller blast radius than adding a `name` attribute to the `Defense` protocol itself (which would touch all 8 concrete defense classes) — the composer already knows each member's name at construction time, so the name only needs to travel with the `DefenseStack` instance, not live on every `Defense`. Concretely:

- `resolve_defense` (`registry.py`) stays exactly as-is — one name in, one `Defense` out.
- New `resolve_defense_stack(name: str) -> DefenseStack` in `registry.py`: splits `name` on `"+"` (e.g. `"spotlighting+guard_model"`), resolves each part via `resolve_defense`, returns `DefenseStack([(part, resolve_defense(part)) for part in name.split("+")])`. A name with no `"+"` behaves identically to today (`DefenseStack([(name, resolve_defense(name))])`) — this is why it's safe to swap in everywhere `DefenseStack([resolve_defense(name)])` is built today, not just in new composition code paths.
- Both adapters gain the ability to log `defense_event`/`cost_record` rows per stack member (reading `defense_stack.last_member_results` after each hook call, and `defense_stack.defenses` — now `list[tuple[str, Defense]]` — when writing `cost_record` rows) instead of the single outer `defense_name` string. `tool_call.blocked_by_defense` should record *which member* blocked, not just that the stack did.
- `config/schema.py`/`config/loader.py` need **zero changes**: `defenses: list[str]` and `RunSpec.defense: str` already accept an arbitrary string; a composition config just lists `"spotlighting+guard_model"` as one of the strings. `run.defense_stack` (a `TEXT` column) stores the composite name exactly as today.
- **Migration list** (every current `DefenseStack(...)` call site — confirmed by grep, 6 files): `sweep/runner.py:158`, `adaptive/sweep.py:288` (both production call sites — switch to `resolve_defense_stack`), `tests/test_defense_stack.py`, `tests/test_agentdojo_adapter.py`, `tests/test_mcp_adapter.py`, `tests/test_adaptive_trial.py` (all construct `DefenseStack([...])` directly — need the tuple-list shape).

This is genuinely the riskiest piece of Sprint 6, not the "2h" the original estimate implies once `_run_trial_point`/adaptive per-round attribution is included — flagged here the same way S5-03 was flagged in Sprint 5's preamble, not discovered mid-week.

**D2 — "Top-4 defenses" cannot be picked by ASR; every defense ties at `0.000` against the local models.** `results/static_baseline.md`/`results/mcp_suite.md`/`results/architectural_defenses.md` all show `ASR = 0.000` for every one of the 8 registered defenses against `llama3.2:3b`/`llama3.1:latest` — the only non-zero cell in the entire project so far is `no_defense`/`important_instructions`/`openai/gpt-oss-120b` (S2-11's Groq slice), and defenses were never run against that model. There is no real security signal to rank defenses by.

**Decision:** pick the top-4 on **mechanism diversity**, not a measured metric that doesn't differentiate them, and document the criterion plainly in `docs/notes/composition.md` rather than presenting it as data-driven when it isn't. Candidate criterion: prefer defenses that (a) have a real, structurally-guaranteed operational effect — `ToolAllowlist` and `CapabilityEnforcement` genuinely block (`on_pre_tool_call`), `GuardModel`'s `on_tool_result` `BLOCK` is a documented no-op — and (b) span different mechanism families (prompt-level: `spotlighting`/`instructional_prevention`; detection-only: `guard_model`/`canary`; architectural blocking: `tool_allowlist`/`capability_enforcement`) so a composed pair tests a genuinely different interaction, not two near-identical layers. Confirm this reasoning against the real per-defense utility-tax and cost numbers already in `results/static_baseline.md`/`results/architectural_defenses.md` before finalizing — a defense with a large, unexplained utility tax is also a legitimate reason to include or exclude it. This is a judgment call the *plan* cannot make for you; the checklist below makes it an explicit, documented first step of S6-01 rather than an assumption baked into a config file.

**D3 — S6-05's "6 models" needs new client code, not just new config rows.** `clients/factory.py::build_model_client` only implements `ollama` and `groq` providers today; anything else raises `ValueError`. Checking `configs/models.yaml` against this: L1/L2 (ollama) are pulled and working; **L3 has no model picked or pulled** (`model: null`, `status: not_pulled`); **L4 (`google_ai_studio`) and L6 (`openrouter`) have no client implementation at all** — L4's `status: key_verified` only means the API key was checked with a bare `GET /v1beta/models`, not that this project can call it. S6-05 as scoped in the sprint plan ("expand model sweep to 6 models... 3h + wall") silently assumes this infrastructure already exists; it doesn't. Broken out below into real sub-steps (pick+pull L3, write two new client classes, wire them into the factory, verify each with one live call) *before* the sweep itself runs.

**D4 — S6-07's ROC curve has no settled ground-truth signal, and this project has never needed one before.** Every prior guard-model number (`results/static_baseline.md`'s "Guard model (D4) score distribution" section) is a plain descriptive summary — it never had to decide, per tool result, whether that specific result *was* the injection point. A ROC curve needs exactly that: a binary ground-truth label per `guard_model` score, not per episode. Two considerations found digging into AgentDojo's injection mechanism (`agentdojo/task_suite/task_suite.py::load_and_inject_default_environment`) and this project's own adaptive machinery:

- For **adaptive trials**, the exact injected payload text is already recorded verbatim (`adaptive_round.payload_text`) — a tool result's content containing that substring is a clean, already-available positive-label signal.
- For **static (non-adaptive) attacked episodes**, the payload is generated fresh at run time via `attack.attack(user_task, injection_task)` and only its *effect* (the tool result it produced) is recorded — the payload text itself is not stored as a separate field anywhere. Getting a per-tool-result ground truth for the static population needs either (a) re-deriving the payload (re-calling `attack.attack` with the same task/injection-task pair, checking determinism first) or (b) a coarser proxy — labeling every tool result in an *attacked* episode as positive and every tool result in a *benign* episode as negative, accepting that non-injection-point tool results in an attacked episode are mislabeled noise.

**Decision:** don't resolve this in the plan — make "decide and document the ground-truth signal, with the tradeoff stated plainly" the explicit first sub-step of S6-07 (below), the same way D7/D8's harder calls got front-loaded in Sprint 5's preamble instead of discovered mid-task.
